Here is a proposed schema for the `raw_events` table and the logic for the "Chain Identifier."

### 1. Proposed Schema: `raw_events`

```sql
CREATE TABLE raw_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_type TEXT NOT NULL,      -- 'human_chat', 'llm_chat', 'chain', 'soul'
    project TEXT NOT NULL,          -- 'mm', 'ac', 'personal'
    
    -- For Deduplication & Threading
    external_id TEXT UNIQUE,        -- chain_id:msg_id, session_id:turn_idx, or telegram_id
    chain_id TEXT,                  -- 'vtx', 'seq_130', etc.
    
    -- Participants
    from_id TEXT,                   -- 'ac_ceo', 'gleb', 'assistant'
    to_id TEXT,                     -- 'ac_term', 'all'
    participants TEXT,              -- JSON array of all involved (e.g. from footer)
    
    -- Content & Time
    timestamp DATETIME NOT NULL,
    content TEXT NOT NULL,
    summary TEXT,                   -- Optional LLM-generated one-liner
    
    -- Processing Metadata
    ingested INTEGER DEFAULT 0,     -- 1 if converted to wiki
    signal_strength REAL DEFAULT 1.0, -- Noise score (LLM-assigned or rule-based)
    tags TEXT,                      -- JSON array
    
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_event_chain ON raw_events(chain_id);
CREATE INDEX idx_event_project ON raw_events(project);
CREATE INDEX idx_event_ingested ON raw_events(ingested);
```

### 2. The "Chain Filter" Logic
To handle your rule about LLM chats containing chain footers, the ingestion script (e.g., `import-claude.ts`) should follow this logic:

1.  **Read the Message.**
2.  **Check for Footer.** Look for the delimiter `---` followed by `chain:`.
3.  **Branch Ingestion:**
    *   **IF CHAIN FOUND:**
        *   Extract `chain_id`, `from`, `to`, and `participants`.
        *   Set `source_type = 'chain'`.
        *   Set `external_id = chain_id + "_" + message_seq` (to ensure absolute dedup).
    *   **ELSE (Standard Chat):**
        *   Set `source_type = 'llm_chat'`.
        *   Set `external_id = session_id + "_" + turn_idx`.

### 3. Why this is better for Deduplication
If we import from multiple sources (e.g., I import my Claude session, and you also import a shared log), the `external_id` (composed of the Chain ID and Message ID) ensures we **never store the same chain message twice**. 

We can then run a query like:
`SELECT * FROM raw_events WHERE chain_id = 'vtx' ORDER BY timestamp ASC`
This gives us a perfect, noise-free reconstruction of a cross-agent conversation, even if the messages were originally scattered across 5 different session files.
